## Highlights

### Transport-neutral Chenile services

`@ChenileController` is now supplied by `chenile-core`, while retaining its
existing package name for source compatibility. A plain Spring bean can become
a Chenile controller without `@RestController`, a servlet request, an HTTP
route, or a `chenile-http` dependency. Headless controllers use
`@ChenileOperation` and `@ChenileBody` and can serve in-process,
event-driven, and serverless workloads.

The common annotation-initialization lifecycle now lives in core. The HTTP
initializer inherits it and adds only Spring MVC controller selection and
mapping behavior.

→ [Annotation-based Chenile services]({{ '/concepts/annotation-based-services/' | relative_url }})

### Simplified Spring MVC mappings

One `SpringMvcMappingProducer` now handles all five existing composed Spring
mapping annotations and direct `@RequestMapping` declarations. A Chenile
operation must have one supported HTTP verb and one route; invalid ambiguous
mappings are rejected during startup instead of being silently reduced.

### Service-registry publication controls

`@ChenileController(registerInServiceRegistry = false)` suppresses publication
for one service while retaining it in local Chenile configuration. For a whole
package that should consume metadata but publish nothing, configure:

```properties
chenile.service.registry.read-only=true
```

Read-only mode retains registry reads and local cache loading. It prevents both
automatic startup publication and direct delegate `save(...)` calls before an
outbound HTTP write occurs.

### JGen headless-service blueprint

The new `chenile-headless-service` blueprint generates a non-HTTP Chenile
service and prompts for registry publication. It requires Chenile `2.1.31` or
newer. More generally, blueprints can declare `sinceVersion`; JGen validates
it through its OWIZ processor chain before hooks or generated files run.

### JGen complete ecosystem blueprint

`chenile-ecosystem` composes existing JGen blueprints to generate an HTTP
service and its primary mini monolith. Optional prompts add a separate service
registry host with delegates, cconfig in the primary monolith, a headless
service with its own mini monolith, and a MyBatis query service with a
query-controller mini monolith. Composed projects are generated in isolation
before being placed together, so their filename processing cannot alter one
another. Each ecosystem has an enclosing Maven reactor parent POM that builds
all selected generated projects; their project-root POMs inherit from it.

### Diagnostics and BDD helpers

`CANNOT_INVOKE_TARGET` diagnostics now retain the target operation, exception
type, and underlying message. REST Cucumber utilities add collection assertions
for scalar values and arbitrary item key/value pairs.

### Database-backed process definitions

`process-service` now provides `DatabaseProcessConfigurator`. Set
`chenile.process.configurator=database` to read each `ProcessDef` JSON value
from `process_definition`, keyed by process type. The classpath JSON
configurator remains the default for compatibility.

### Trigger ingress, cron schedules, and execution history

- The new `chenile-trigger` module normalizes external inputs into existing
  synchronous Chenile events. Persistent Quartz crontabs can create
  `ProcessCreate` events with typed arguments and tenant context.
- `TriggerLog` is a trigger-specific idempotency ledger, not a general-purpose
  process audit log. Separate trigger-execution history captures start/end
  times, generated events, payloads, outcomes, and linked processes.
- Processes retain trigger, parent, and predecessor lineage. Completion history
  records emitted events and their generation time for end-to-end inspection.

### Process definitions and completion chaining

- `ProcessDef.config` is the shared configuration for splitters, executors,
  and aggregators. Database-backed definitions have a HashMap-based cache with
  explicit invalidation after committed definition changes.
- `ProcessCompletedEvent` extends `ProcessDto`, and the process manager
  subscribes to completion ingress. A definition's `predecessorProcessType`
  determines which completed type starts it; `predecessorArgs` selects
  `INPUT`, `OUTPUT`, or `BOTH` (the default).
- The unused dormant state and activate event are removed. Leaf processes
  start at execution; composite processes start at splitting. Obsolete
  activation and configured-successor test fixtures have been removed.

### Optional durable outbox with shared commands

- `process-outbox` persists transition effects in the same transaction as
  process state. It supports lease-fenced claiming, retries/backoff,
  transactional consumer receipts, dead-letter visibility, and selected replay.
- Four extensible commands implement one lifecycle contract:
  `CreateSubProcessCommand`, `SignalParentCommand`,
  `EmitCompletedCommand`, and `StartWorkerCommand`. Each owns its
  `enqueue`, `dispatch`, and `onDead` behavior and JSON payload.
  Persistence contains shared delivery metadata rather than command-specific
  columns.
- Entry actions use those same commands when durability is disabled, avoiding
  duplicate inline implementations. Inline execution remains synchronous;
  durable execution returns before queued work finishes.
- Version-one durability covers framework-managed creation, parent signaling,
  worker handoff, and completion chaining. Application completion listeners
  remain best-effort after commit; external workers must deduplicate dispatch IDs.
- Exhausted worker-start delivery transitions its process to an error terminal
  instead of leaving the tree waiting indefinitely. Other dead commands require
  diagnosis and explicit replay; dead callbacks are not a durable compensation queue.
- Fixes preserve tenant context through JPA flush, hydrate child validation
  errors before detached aggregation, and commit inline JDBC worker enqueueing
  even when connection-pool auto-commit is disabled.

### Management API, React dashboard, and runnable server

- The opt-in query/update API supports cron administration, manual triggers,
  definition inspection/editing, paged process/status queries, child and
  successor navigation, completion history, and connected execution traces.
- The React dashboard links trigger executions, process trees, completion
  events, and downstream processes into an end-to-end execution view.
- `process-admin-server` packages an executable Spring Boot host with database
  definitions, Quartz, the outbox, and JDBC worker delivery. Development uses
  persistent H2; production requires PostgreSQL and explicit schema migrations.
- A required administrator key of at least 32 characters protects every HTTP
  route in the standalone host. The UI keeps the key only in memory; no default
  secret is shipped. The key is shared across tenants, not per-user authorization.
- The standalone administrator host does not implement business workers.
  Application workers must consume queued work and report results.

### JGen process-management mini-monolith blueprint

- `chenile-process-management` accepts a validated process graph and generates
  API, service, configuration, and executable-package Maven modules. It supports
  arbitrary hierarchy depth, multiple child types, predecessor argument selection,
  and typed input DTOs.
- Every process exposes a local Chenile service and HTTP ingress; service-registry
  publication is configurable independently of local availability.
- Generation emits `defs.json` or initializes missing database definitions,
  optionally seeds cron triggers, and preserves existing edited rows on restart.
- Runnable FileUpload/ChunkUpload and three-level examples split files into real
  chunks, execute leaf reads/checksums, and aggregate results and errors. Custom
  workers are explicit scaffolds requiring application implementations, not
  invented business logic. The examples do not upload files to a remote storage service.
- Background polling supports both inline commands and durable outbox delivery.
  Generated tests cover startup, definitions, cron linkage, successful execution,
  error aggregation, and both delivery modes.
- The existing batch blueprint now uses the unified configuration and predecessor
  fields. Ecosystem input metadata has also been reformatted without changing its contract.

### Supporting maintenance and documentation

- Parent dependency management includes the trigger artifact and the earlier
  logger artifact declaration; the active trigger runtime uses `TriggerLog`.
- Scheduler initializer documentation now describes scheduler registration.
  The legacy Chenile STM XML reader reuses an existing state descriptor when
  processing the same state ID instead of replacing it.
- Developer documentation adds trigger architecture, process management, outbox,
  administration/UI setup, and a Temporal comparison. Introductory video assets,
  subtitles, presentation decks, and explanatory diagrams are updated.

## Upgrade notes

Once published, point your application's parent (or `chenile.*.version` properties) at `2.1.31` and rebuild — the 11 repositories move together under `chenile-parent`.

```xml
<parent>
  <groupId>org.chenile</groupId>
  <artifactId>chenile-parent</artifactId>
  <version>2.1.31</version>
</parent>
```

Existing HTTP controllers continue to work. New headless controllers should use
`@ChenileOperation` for every operation and `@ChenileBody` for an exchange-body
parameter. Direct `@RequestMapping` methods must have one supported HTTP verb
and one route.

## Process-management migration and operational notes

- Replace `splitterConfig`, `executorConfig`, and `aggregatorConfig` with
  `config`. Replace configured `successors` with successor definitions declaring
  `predecessorProcessType`; choose `predecessorArgs` explicitly if the default
  `BOTH` is unsuitable. Remove dormant-state and activate-event assumptions.
- Provision the process/trigger schema and separate execution/completion history.
  Use `TriggerLog` for trigger idempotency, not process-create audit events.
- Opt into durability with `chenile.process.outbox.enabled=true`. Process JPA,
  outbox JDBC, and JDBC worker delivery must share a datasource and transaction
  manager. PostgreSQL is the reference database.
- For an earlier column-based outbox prototype, stop producers/dispatchers,
  back up the table, and apply the packaged transactional JSON migration before
  starting new code. Do not mix old and new command formats.
- Apply outbox, worker-queue, and history SQL resources through production
  migration tooling. History initialization assumes the process table exists.
  Development schema initialization is not a production upgrade strategy.
- Supply `PROCESS_MANAGEMENT_API_KEY` from a secret manager. Put a secured
  HTTPS gateway in front of the loopback-bound administrator host before exposing
  it. The shared key grants administrator access across tenants.
- Use one scheduler owner for the current cron implementation. Trace queries
  are bounded, and definition editing requires the database configurator.
- Generated process mini-monoliths require the enhanced `2.1.31` runtime.
  These source updates do not constitute a Maven Central deployment; install
  compatible artifacts locally until publication is completed.

## Verification

The implementation work completed 136 process-management tests (including
PostgreSQL durability and tenant-flush regressions), 21 JGen reactor tests,
and 32 generated runnable-application tests spanning JSON/database definitions,
registry settings, hierarchy depths, and inline/durable delivery. A custom
multi-child scaffold compiled and passed startup tests. An executable generated
application was smoke-tested through authenticated HTTP ingress to terminal
completion. Final release-preparation checks repeated all 136 process-management
tests with PostgreSQL enabled, with zero failures, errors, or skips. The UI passed
nine unit tests, four desktop/mobile browser tests, and its production build.
Legacy STM passed 29 tests. The documentation site built successfully, with
existing non-fatal Liquid-example warnings on unrelated concept pages.
