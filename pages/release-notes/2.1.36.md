# Chenile 2.1.36 <span class="pill">in development</span>

**Not released.** The train moved to 2.1.36 after 2.1.35 was tagged. These notes track work merged since then and
will change before the release.

## One event model: everything but HTTP is an event

Other than HTTP, Chenile now treats everything as a [Chenile event](/concepts/17-events/): an internal event that
operations subscribe to, mapped from an external happening such as a schedule coming due, a file landing in a
watched folder or a message on a topic. Schedules and file watch no longer name a service and operation; they fire
an event. See [events, schedules and file watch](/developer/entry-points/) and the decision record,
chenile-others `docs/adr/0001-unified-chenile-events-and-scheduling.md`.

- **chenile-trigger (new, chenile-core).** `TriggerService`, `TriggerInput`, `TriggerResult`, `TriggerStatus`, the
  standard header names (`TriggerHeaders`) and source values, and `DirectTriggerService`, the default in-memory
  implementation (deduplication for `chenile.trigger.dedupe.retention`, default `PT24H`, up to
  `chenile.trigger.dedupe.max-entries`, default 100000). Process management's durable `EventTriggerService`
  replaces it when `trigger-service` is present.
- **chenile-scheduler, rebuilt.** One `SchedulerDefinition` (id, name, cron expression, timezone, event id,
  payload, headers, tenant, enabled) from JSON files or code, held by `ChenileScheduler`, fired through the
  `TriggerService` with the key `schedule:<id>:<scheduled fire time>`. Quartz is Spring Boot's (`spring.quartz.*`)
  and can run clustered on the JDBC job store; the job data holds only the schedule id, and the `chenile-quartz`
  Liquibase changelog creates Quartz's tables.
- **chenile-scheduler-db (new).** Database schedules over `POST|GET /schedule` and `GET|DELETE /schedule/{id}`,
  tenant-scoped, scheduled after commit, read from the database when they fire on any node. Liquibase context
  `chenile-scheduler-db`.
- **chenile-filewatch.** Each record fires the definition's `eventId` (defaulting to the file watch id) through the
  `TriggerService`, keyed by the file's SHA-256 and the record index, so a reprocessed file fires nothing new.
- **chenile-mqtt: topics can raise Chenile events.** `chenile.mqtt.topic-bindings` binds an MQTT topic to an event
  id; a message on that topic raises the event through `EventProcessor`, so every subscribed operation runs, as for
  Kafka, Azure Event Hubs and in-JVM pub/sub. Bindings are opt-in and exact-match. `@ChenilePubSub` invocations
  (`<subscribe-topic>/<operation>`) are unchanged and still go through `PubSubEntryPoint`. See
  [messaging transports](/developer/messaging-transports/#mqtt).
- **Process management.** `trigger-api`, `crontab-api` and `crontab-service` are removed. The admin API's
  `/crontabs` become `/schedules`, `/executions` filters by `scheduleId`, and the console's Cron triggers tab is now
  Schedules.

## chenile-mcp: tool calls go through the Chenile entry point

An MCP tool call used to invoke the service bean directly, skipping the interception pipeline. `ChenileToolCallback`
now builds a `ChenileExchange` and calls `ChenileEntryPoint`, like every other transport adapter, so agent calls get
the same header validation, pre- and post-processors, transformation, service selection, trajectories and service
interceptors as HTTP calls.

- The BODY parameter is passed as JSON and typed inside the highway by the transformer and any body type selector.
  HEADER and HEADERS parameters become headers. Polymorph fixed values are bound the same way. Operations with
  multi-part parameters are not exposed as tools.
- The exchange carries `x-chenile-entry-point: MCP`, with the tool name as sub-type.
- With `spring.ai.mcp.server.protocol=STREAMABLE` on the WebMVC server, Chenile installs the transport with a context
  extractor that passes the caller's `x-` headers and `Authorization` header into the exchange. A caller cannot
  override the entry point.
- A failed call returns a tool error carrying the `GenericResponse` error as JSON.
- `chenile-mcp` now depends on `spring-ai-mcp`; `spring-ai-starter-mcp-server-webmvc` is optional.

### Upgrade notes

- **Removed from chenile-scheduler:** `SchedulerInfo`, `SchedulerBuilder`, `ChenileSchedulerInitializer`,
  `ScheduledJob`, the task launchers and dispatcher, and `SchedulerExecutionStore` with its JDBC schema. Rewrite each
  `*-schedule.json` as a `SchedulerDefinition` with an `eventId`, and subscribe the operation to that event
  (`@EventsSubscribedTo` or `eventSubscribedTo`).
- **MCP polymorph payloads:** a `ChenilePolymorphVariant`'s parameter types now only shape the schema the agent sees.
  The payload is typed in the highway, so an operation whose variants carry different payload types needs a
  `@BodyTypeSelector` that sets a body type for every variant (a selector that sets none leaves the body a string).
- **MCP security:** agent calls now pass the security and tenancy interceptors. MCP clients must send the headers
  (or bearer token) those interceptors expect.
- **File watch:** subscribe operations with `eventSubscribedTo`; an operation's `fileWatchId` is no longer used.
  Header-file properties that don't start with `x-` move from the event headers to the trigger context.
- **Crontabs:** the `chenile_crontab` table is no longer used and its rows are not migrated; recreate schedules
  through `/schedule` or the console.
- **Quartz bean:** the `quartzScheduler` bean now comes from Spring Boot's Quartz auto-configuration. An application
  that defines its own bean of that name must drop it or exclude `QuartzAutoConfiguration`.
- **JGen:** the process-management blueprint's `cronSpec` input is now `scheduleSpec`; the generated projects need
  Chenile 2.1.36.

## JGen and stm-cli have their own releases

Until now JGen and stm-cli shared Chenile's version number. From now on they are released on their own cadence,
and each is built only against Chenile versions that are already released.

- **JGen** continues at **2.5.1**. Everything added to JGen since 2.1.35 ships in JGen 2.5.1, not in Chenile 2.1.36:
  generated Git repositories, standalone blueprint projects, template-only blueprints, catalogs, JavaScript hooks,
  extensions (template engines including Pebble, language packs, path tags), `_DoT_` for dotfiles, and the
  `GITHUB_REPOSITORY` and `PATTERN` rules. Its libraries move to the Maven group `org.chenile.jgen`. See
  [JGen releases and versions](https://jgen.chenile.org/releases/).
- **stm-cli** starts its own line at **1.0.0** in its own repository,
  [ajapros/stm-cli](https://github.com/ajapros/stm-cli), and installs with
  `brew install ajapros/jgen-tap/stm-cli`.

## workflow-utils: the stm-cli command moved out

The command-line entry point `org.chenile.workflow.cli.CLI` (and its `VersionProvider`) moved to the stm-cli
project as `org.chenile.stmcli.StmCli`. workflow-utils no longer builds a `jar-with-dependencies`.

`CLIHelper` and `CLIParams` stay in workflow-utils, so code that renders diagrams or test cases from a states XML
is unaffected. That code includes workflow-info, stm-generate-puml and JGen.

If you ran `java -jar workflow-utils-<version>-jar-with-dependencies.jar`, install stm-cli instead.
