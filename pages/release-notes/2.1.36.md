# Chenile 2.1.36 <span class="pill">in development</span>

**Not released.** The train moved to 2.1.36 after 2.1.35 was tagged. These notes cover everything merged on the
`main` branches since then and will be finalized at release.

## Highlights

- **One event model.** Other than HTTP, everything is a [Chenile event](/concepts/17-events/). Schedules, file
  watch, broker topics and posted triggers all raise events that operations subscribe to.
- **chenile-trigger (new).** One contract, `TriggerService`, for every internal event source, with deduplication and
  status. It lives in chenile-core.
- **Schedules, rebuilt.** One `SchedulerDefinition`, Spring Boot's Quartz (clustered if you like), and database
  schedules over REST with the new `chenile-scheduler-db`.
- **MQTT topics can raise Chenile events,** like Kafka, Azure Event Hubs and in-JVM pub-sub already could.
- **MCP tool calls go through `ChenileEntryPoint`.** AI agents now get the same policies as every other caller,
  including the caller's tenant, trajectory and authorization headers.
- **One entry point, documented.** The new [How it works](/how-it-works/) page shows every transport adapter
  handing off to `ChenileEntryPoint`.
- **Process management** uses the core trigger contract, replaces crontabs with schedules, and polls every tenant's
  outbox in database-per-tenant deployments.
- **JGen and stm-cli** are now released on their own cadence (JGen 2.5.1, stm-cli 1.0.0).

## One event model: everything but HTTP is an event

HTTP calls an operation. Everything else raises an internal Chenile event, and the operations subscribed to it
run. Schedules and file watch no longer name a service and operation; they fire an event. An operation subscribes
with `@EventsSubscribedTo` (or `eventSubscribedTo` in a JSON definition), and `EventProcessor` creates one exchange
per subscriber, each run through the full interception pipeline.

| External happening | Mapped by | Event id |
|---|---|---|
| A cron schedule becomes due | `chenile-scheduler`, `chenile-scheduler-db` | the schedule's `eventId` |
| A file lands in a watched folder | `chenile-filewatch` | the file watch's `eventId` (defaults to its id) |
| A message arrives on a topic | `chenile-messaging` | Kafka: `chenile.kafka.consumer.topic-bindings` or the topic; MQTT: `chenile.mqtt.topic-bindings` |
| A trigger is posted or raised in code | `POST /trigger`, `TriggerService.trigger(...)` | the input's `eventId` |

See [Everything but HTTP is an event](/concepts/17-events/), the developer reference
[events, schedules and file watch](/developer/entry-points/), and the decision record in chenile-others,
`docs/adr/0001-unified-chenile-events-and-scheduling.md`.

### chenile-trigger (new, in chenile-core)

`org.chenile.trigger` is the one contract that every internal event source raises events through.

- **API.** `TriggerService.trigger(TriggerInput)` returns a `TriggerResult` (the trigger id), and
  `TriggerService.status(triggerId)` returns a `TriggerStatus`. `TriggerInput` carries `eventId`, `payload`,
  `headers`, `idempotencyKey`, `source`, `triggerTime` and a trigger context.
- **Validation.** An event id is required, every header must start with `x-`, and the tenant must match the
  caller's.
- **Standard headers** (`TriggerHeaders`): `x-chenile-event-source`, `x-chenile-trigger-id`, the tenant header,
  `x-chenile-schedule-id`, `x-chenile-scheduled-fire-time`, `x-chenile-fire-time`, `x-chenile-file-watch-id`,
  `x-chenile-file-name`, `x-chenile-record-index` and `x-chenile-topic`. Subscribers can bind them as `HEADER`
  parameters.
- **Sources** (`TriggerSources`): `CRON`, `FILE`, `PUBSUB`, `API`, `EXTERNAL`.
- **`DirectTriggerService`, the default.** It raises the event at once and returns when every subscriber has
  finished. "No subscriber" or a subscriber exception is a failure: it is thrown back to the caller, and the
  idempotency key is released so the trigger can be retried. The caller's `ContextContainer` is restored afterwards.
  A repeated idempotency key (per tenant and event) returns the first trigger's id without raising the event again.
  Keys and statuses are kept in memory on the node for `chenile.trigger.dedupe.retention` (ISO-8601, default
  `PT24H`), up to `chenile.trigger.dedupe.max-entries` (default 100000). Status is tenant-scoped.
- **Wiring.** `DirectTriggerAutoConfiguration` registers it when an `EventProcessor` exists and no other
  `TriggerService` does. With process management's `trigger-service` on the class path, the durable
  `EventTriggerService` replaces it.
- Covered by unit tests and a Cucumber feature (`trigger.feature`).

### chenile-scheduler, rebuilt

- **One definition.** A schedule is a `SchedulerDefinition`: `id` (also the Quartz job and trigger key), `name`,
  `cronExpression` (Quartz syntax, with seconds), `timezone` (default `UTC`), `eventId`, `payload` (JSON text,
  converted to each subscriber's body type), `headers` (names must start with `x-`), `tenant`, `enabled` and
  `description`.
- **Sources.** Definitions are read from JSON files found through `chenile.scheduler.json.package` at startup, or
  registered from code with `ChenileScheduler`.
- **Firing.** A due schedule fires its event through `TriggerService`, with source `CRON` and the idempotency key
  `schedule:<id>:<scheduled fire time>`, so a fire time is handled once even if Quartz fires it again.
- **Quartz.** The scheduler now uses Spring Boot's Quartz auto-configuration (`spring.quartz.*`), so it can run
  clustered on the JDBC job store. The job data holds only the schedule id, which is safe for a clustered store.
  The `chenile-quartz` Liquibase changelog creates Quartz's tables.

### chenile-scheduler-db (new)

- Database-held schedules over REST: `POST /schedule`, `GET /schedule`, `GET /schedule/{id}` and
  `DELETE /schedule/{id}`.
- Schedules are tenant-scoped, scheduled in Quartz after the transaction commits, and read from the database when
  they fire, so any node in a cluster can fire them.
- Liquibase context `chenile-scheduler-db`.

### chenile-filewatch

- Each record of a processed file fires the definition's `eventId` (defaulting to the file watch id) through
  `TriggerService`, with source `FILE`.
- The idempotency key is `file:<file watch id>:<file name>:<SHA-256 of the file>:<record index>`, so reprocessing
  an unchanged file fires nothing new.
- Header-file properties that start with `x-` become event headers; the others go into the trigger context.

## Messaging: MQTT topics can raise Chenile events

`chenile-mqtt` now supports the event model, as Kafka, Azure Event Hubs and in-JVM pub-sub already did.

```yaml
chenile:
  mqtt:
    qos: 1                                      # QoS for the bound topics (default 1)
    topic-bindings:
      "[devices/telemetry]": telemetryReceived  # MQTT topic -> Chenile event id
```

- A message on a bound topic raises the event through `EventProcessor`, so every subscribed operation runs. The
  exchange carries the MQTT user properties as headers, with `x-chenile-entry-point: PUB_SUB` and sub-type `MQTT`.
- Bindings are validated at startup: a binding to an unknown event id fails startup. The bound topics are
  subscribed once the application is ready, and again after a reconnect.
- Bindings are opt-in (unlike Kafka, MQTT does not subscribe to every event id by default, because an MQTT broker is
  often shared with devices) and match topics exactly; MQTT wildcards are not supported in bindings.
- If no subscriber handles the event, or one fails, the exception is thrown and the message is not acknowledged, so
  the broker can redeliver it at QoS 1 or 2.
- `@ChenilePubSub` invocations, where `<subscribe-topic>/<operation>` names one operation, are unchanged and still
  go through `PubSubEntryPoint`. When a topic is bound to an event, the event binding wins.

See [messaging transports](/developer/messaging-transports/#mqtt).

## MCP: tool calls go through the Chenile entry point

Before 2.1.36, an MCP tool call invoked the service bean directly by reflection and skipped the interception
pipeline. Now `ChenileToolCallback` is a transport adapter like the others: it builds a `ChenileExchange` and calls
`ChenileEntryPoint`. Agent calls therefore get header validation, pre- and post-processors, transformation, service
selection, trajectories, mocks and the service interceptors, which is what the [MCP guide](/developer/mcp/) always
promised.

- **Binding.** Each tool parameter is bound by its `HttpBindingType`. The `BODY` parameter is passed as JSON and
  typed inside the highway by the transformer and any body type selector, exactly as for HTTP. `HEADER` parameters
  become headers, and a `HEADERS` parameter is merged into the headers. Polymorph fixed values are bound the same
  way.
- **Entry point.** The exchange carries `x-chenile-entry-point: MCP`, with the tool name as the sub-type.
- **Caller headers.** With the Streamable HTTP WebMVC server (`spring.ai.mcp.server.protocol=STREAMABLE`, the jgen
  default), Chenile installs the transport with `ChenileMcpHeaderExtractor`. It passes the caller's `x-` headers
  (tenant, trajectory and the other Chenile headers) and the `Authorization` header into the exchange. They are
  copied before the entry point header and the tool parameters, so a caller cannot override those. Spring AI's own
  transport auto-configuration backs off.
- **Results.** On success the tool returns the response's payload. On failure it returns a tool error carrying the
  `GenericResponse` error as JSON, so the agent sees Chenile's error codes.
- **Context.** The calling thread's `ContextContainer` is saved and restored around the call.
- **Multi-part.** Operations with `MULTI_PART` parameters are not exposed as tools.
- **Dependencies.** `chenile-mcp` now depends on `spring-ai-mcp`; `spring-ai-starter-mcp-server-webmvc` is
  optional.
- Tests prove that a tool call passes through a service interceptor, that the caller's tenant header arrives, and
  that a faked entry-point header is ignored.

## One pipeline: transport adapters

Every way into a service now goes through a transport adapter that builds a `ChenileExchange` and calls
`ChenileEntryPoint`. Nothing reaches a service bean any other way.

| Adapter | Module | What it serves |
|---|---|---|
| `ControllerSupport` | chenile-http | Spring `@RestController` classes, which stay in the request path |
| `HttpEntryPoint` | chenile-http | Routes from annotation (`@ChenileController`) and JSON definitions; a non-REST `@ChenileController` is only the definition |
| `LocalProxyInvoker` | chenile-proxy | A proxy call to a service in the same deployable (to a remote service, the proxy becomes an HTTP client) |
| `ChenileToolCallback` | chenile-mcp | MCP tool calls |
| `EventProcessor` | chenile-core | Chenile events from brokers, schedules, file watch and triggers |
| `PubSubEntryPoint` | chenile-pub-sub | `@ChenilePubSub` invocations |

`ChenileExchangeBuilder` is a utility for building an exchange, not an adapter.

**Body type selection, clarified.** `TransformationClassSelector` uses an operation-level body type selector, then a
service-level one, and only if neither is configured falls back to the operation's input and `BODY` parameter
metadata, keeping generic types such as `List<Payload>`. A registered selector owns the decision: if it sets no
type, the body is not converted. The rules are now documented in the class.

## Process management

- **Trigger service on the core contract.** `EventTriggerService` now implements chenile-core's
  `org.chenile.trigger.TriggerService`, and the separate `trigger-api` module is removed. Triggers stay durable
  `DISPATCH_TRIGGER` outbox commands.
- **Crontabs replaced by schedules.** `crontab-api` and `crontab-service` are removed; schedules come from
  chenile-scheduler and chenile-scheduler-db. In the admin API, `/crontabs` become `/schedules`, and
  `/executions` filters by `scheduleId`. The console's Cron triggers tab is now Schedules. The admin server's
  Liquibase master changelog and the process blueprint follow.
- **Database-per-tenant outbox polling.** When tenants have their own databases behind a tenant-routing
  `DataSource` (`multi-datasource-utils`), each tenant has its own outbox table. The scheduled task now runs
  `TenantAwareOutboxPoller`: for each tenant it sets the tenant in the context and drains that tenant's outbox, so
  claim, handle, acknowledge and failure transactions all open on that tenant's database. A failure in one tenant is
  logged and the others are still drained. Tenants come from the first of: an `OutboxTenantSupplier` bean,
  `chenile.process.outbox.tenants` (comma-separated), the keys of the `multiTenantTargetDataSources` bean, or none
  (a single poll, as for single-tenant deployments). Adding `multi-datasource-utils` is enough; apply the outbox
  schema to every tenant database. Covered by unit tests and a Cucumber feature (`multi-tenant-outbox.feature`).
- **Docs.** The deployment guide, the deployment schematic and the process management guide describe service
  selection and the typed process work listeners, and use schedules throughout.

## JGen and stm-cli have their own releases

Until now JGen and stm-cli shared Chenile's version number. From now on they are released on their own cadence,
and each is built only against Chenile versions that are already released.

- **JGen** continues at **2.5.1**. Everything added to JGen since 2.1.35 ships in JGen 2.5.1, not in Chenile 2.1.36:
  generated Git repositories, standalone blueprint projects, template-only blueprints, catalogs, JavaScript hooks,
  extensions (template engines including Pebble, language packs, path tags), `_DoT_` for dotfiles, and the
  `GITHUB_REPOSITORY` and `PATTERN` rules. Its libraries move to the Maven group `org.chenile.jgen`. See
  [JGen releases and versions](https://jgen.chenile.org/releases/).
- **stm-cli** starts its own line at **1.0.0** in its own repository,
  [ajapros/stm-cli](https://github.com/ajapros/stm-cli), and installs with
  `brew install ajapros/jgen-tap/stm-cli`.

### workflow-utils: the stm-cli command moved out

The command-line entry point `org.chenile.workflow.cli.CLI` (and its `VersionProvider`) moved to the stm-cli project
as `org.chenile.stmcli.StmCli`. workflow-utils no longer builds a `jar-with-dependencies`. `CLIHelper` and
`CLIParams` stay in workflow-utils, so code that renders diagrams or test cases from a states XML is unaffected:
that includes workflow-info, stm-generate-puml and JGen.

## Upgrade notes

**Schedules**

- Removed from chenile-scheduler: `SchedulerInfo`, `SchedulerBuilder`, `ChenileSchedulerInitializer`,
  `ScheduledJob`, the task launchers and dispatcher, and `SchedulerExecutionStore` with its JDBC schema. Rewrite each
  `*-schedule.json` as a `SchedulerDefinition` with an `eventId`, and subscribe the operation to that event.
- The `quartzScheduler` bean now comes from Spring Boot's Quartz auto-configuration. An application that defines its
  own bean of that name must drop it or exclude `QuartzAutoConfiguration`.
- Process management crontabs: the `chenile_crontab` table is no longer used and its rows are not migrated.
  Recreate schedules through `/schedule` or the console. Clients of the admin API must move from `/crontabs` to
  `/schedules`.

**File watch**

- Subscribe operations with `eventSubscribedTo`; an operation's `fileWatchId` is no longer used.
- Header-file properties that don't start with `x-` move from the event headers to the trigger context.

**Triggers**

- Code that used process management's `trigger-api` (`org.chenile.trigger.*` from that module) now gets the same
  package from chenile-core's `chenile-trigger`. Replace the `trigger-api` dependency with `chenile-trigger`.

**MCP**

- Agent calls now pass the security and tenancy interceptors. MCP clients must send the headers or bearer token
  those interceptors expect; with Claude's connectors, prefer deriving the tenant from the OAuth token.
- A `ChenilePolymorphVariant`'s parameter types now only shape the schema the agent sees. The payload is typed in the
  highway, so an operation whose variants carry different payload types needs a `@BodyTypeSelector` that sets a body
  type for every variant.
- Applications that defined their own `WebMvcStreamableServerTransportProvider` keep theirs, but caller headers then
  reach tools only if that bean sets `ChenileMcpHeaderExtractor` as its context extractor.

**MQTT**

- No change is needed: without `chenile.mqtt.topic-bindings`, MQTT behaves as before.

**Tooling**

- If you ran `java -jar workflow-utils-<version>-jar-with-dependencies.jar`, install stm-cli instead.
- JGen: the process-management blueprint's `cronSpec` input is now `scheduleSpec`, and the generated projects need
  Chenile 2.1.36.
