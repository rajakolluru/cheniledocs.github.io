# Chenile 2.1.35 <span class="pill">in development</span>

**Not released.** The version was bumped to 2.1.35 across the train on October 22, 2026, after 2.1.34 was
tagged. These notes track work merged (or in progress) since then and will change before the release.

## Choose the implementation per request: `serviceSelector`

A Chenile service can now name a **`ServiceSelector`** — `@ChenileController(serviceSelector = "...")`, or
`"serviceSelector"` in a JSON service definition. The selector is a Spring bean implementing
`org.chenile.core.service.ServiceSelector`:

```java
String selectServiceReferenceName(ChenileExchange exchange, ChenileServiceDefinition serviceDefinition);
```

It runs on every invocation inside `constructServiceReference` and returns the bean name of the implementation
to call, or `null` to keep the service's configured `serviceName`. Resolution order is fixed: **mock** mode,
then a **trajectory** override, then the **selector**, then the default bean. A selector bean that is not a
`ServiceSelector` fails startup (error 525). The bean it *returns* is resolved — and its method matched — per
request, so a misnamed bean fails that request rather than startup. See
[choosing the implementation per request](/developer/runtime-internals/#choosing-the-implementation-per-request).

## Typed process work listeners

Process management is the first user of `serviceSelector`. Queue-delivered process work is now typed end to end:

- **New contract** in `process-api`: `WorkListenerService<T>` and the `WorkListenerInput<T>` envelope
  (`processId`, `dispatchId`, `payload`, `execDef`).
- **New worker bases** in `process-delegate`: `ExecutorWorkListener<In, Out>`, `SplitterWorkListener<In, ChildIn>`
  and `AggregatorWorkListener<In, Out, ChildOut>`. Executors and splitters implement
  `doStart(WorkListenerInput<In>)`; the aggregator folds each child with
  `doStart(out, input, childOutput, child)`.
- **Routing.** `processWorkServiceSelector` picks the worker bean from the message's `processType` and
  `workerType` headers — `item` + `EXECUTOR` → `itemExecutor` — and `processWorkBodyTypeSelector` types the
  payload from that worker's generic parameter. Worker bean names are therefore routing keys.
- **Queue message.** `QueueBasedProcessStarter` publishes the `WorkListenerInput` envelope with
  `processType` / `workerType` headers and stamps the process's tenant on each message. The previous
  `WorkerDto` format remains available as `start1()`.
- **Failure semantics.** A worker's own exception is reported to the server as `doneWithErrors`,
  `splitDoneWithErrors` or `aggregationDoneWithErrors`, so the process ends `PROCESSED_WITH_ERRORS` without
  retrying the same input. Callback failures and malformed deliveries still go to Kafka retry and the
  dead-letter topic.
- **Generator and sample.** JGen's process blueprints generate the listener and workers in this shape (the
  generated `doStart` hooks return defaults instead of throwing), and `chenile-samples/p1` is migrated — see the
  [process deployment tutorial](/developer/process-deployment-tutorial/).

**Upgrading:** the shared `BatchServiceBase` bean from 2.1.34 is replaced by a fallback that fails if no worker
was selected. Move workers to the typed listener bases and name their beans `<processType>Executor`,
`<processType>Splitter`, `<processType>Aggregator`. `SplitterBase`, `ExecutorBase`, `AggregatorBase` and
`BatchServiceBase` remain in `process-delegate` for legacy `WorkerDto` listeners.

## Process console

The crontab form in `process-ui` has a **Quartz cron-expression builder**: pick every-N-minutes, hourly, daily,
weekdays, weekly or monthly and a time, and it fills the expression (for example `0 30 9 ? * MON-FRI`), which
stays editable.
