How it works

One service, many transports

A Chenile service is defined and registered once. HTTP, proxies, AI agents, pub-sub brokers and triggers each reach it through a transport adapter, and every adapter hands off to the same ChenileEntryPoint and chenile-highway. Your policies run once, in one place, whatever the caller.

Reading the picture

Define once, subscribe many ways

1 · Register a Chenile service

A @ChenileController or a JSON definition describes the service once: its operations, parameters and body types. At startup it registers HTTP routes and event subscriptions. A non-REST @ChenileController is never invoked on a request; it is only the definition.

2 · Subscribe to HTTP

A Spring @RestController sits in the request path: it receives the request and deflects it through ControllerSupport. Annotation and JSON services skip it, because HttpEntryPoint handles their routes directly.

3 · Subscribe to a Chenile event

Other than HTTP, everything is an event. Kafka, Azure Event Hubs, MQTT and JVM pub-sub topics, schedules, file watch and posted triggers all raise events through EventProcessor, which creates one exchange for each subscribed operation.

4 · Proxies and agents

A Chenile proxy to a local service calls ChenileEntryPoint through LocalProxyInvoker; to a remote service it becomes an HTTP client, so the call comes in through that service’s HTTP entry point. An MCP tool call enters through ChenileMCP, so AI agents get the same security, tenancy and logging as every other caller.

The adapters

Every door leads to one entry point

Each adapter turns its transport's message into a ChenileExchange and calls ChenileEntryPoint. Nothing reaches a service bean any other way.
